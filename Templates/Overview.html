Protocol overview

Threat model

The problem: Session cookies act as long-lived bearer tokens—once exfiltrated by malware, attackers can replay them from any device to bypass MFA and passkeys.

The attacker: A malicious app running on the victim's device which was not present during session registration time.

Notes.

Protocol overview

Security model

The premise: As long as a session was registered on an uncompromised device, the server has cryptographic certainty that the session key cannot be exfiltrated to a different device—forcing malware to act locally.

The protection: Bind session continuity to an unexportable private key securely stored by the browser so stolen tokens become useless once short-lived cookies expire.

Caveat

The security model intentionally decouples the protocol from the platform storage primitive: user agents choose how to protect private keys (TPMs, secure enclaves, OS key APIs, or process isolation) without exposing hardware identity or device state to the server.

Notes.

How it works at a high level

  1. Server sends the registration header Secure-Session-Registration to the client.
  2. User agent creates a new key pair, sign the challenge present in the header, and sends it back to the registration endpoint.
  3. Server verifies the challenge signature, stores the client's public key, and responds with the registration instruction JSON.
  4. User agent starts watching for cookies listed in the instruction JSON expiration.
  5. User agent calls the refresh endpoint when cookies are expired or about to.
  6. Upon successful refresh, the server gives the client new (short-lived) cookies.
